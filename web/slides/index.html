Why

Why it exists

Models reinvent the wheel. The same functions, written fresh in every session, with no memory that any of it was ever solved.

haversine

The distance formula, re-derived from scratch in a helper file nobody will open again.

delimiter sniff

Comma or semicolon or tab, guessed again — this time with slightly different heuristics.

slugify

Diacritics stripped one more way, so two parts of the same product disagree on a URL.

The problem isn’t that AI writes bad code — it’s that it writes good code cheaply enough that nothing ever accumulates.

Why

The idea

Before an agent solves a task, it asks its local manager — CFCM — one question: do we already have this?

If yes

It runs a sealed, tested implementation. Same input, same output, every session, on every machine that has the registry.

If no

It writes the code as usual — and can offer what it wrote back to the registry as a candidate.

Centralize knowledge, decentralize execution.

How it works

The flow

Everything runs on the developer’s own machine. No central execution service.

Using it

What search returns

$ cfcm search "coordinates for an address"

MATCH  confidence 0.867  (5.5 ms)
  CapFoundry.geo.geocode  1.0.0  [public]
    Resolve an address or place name to coordinates
    matched on: aliases · description · exampleQueries · summaries · tags

It tells you why it matched, not just how confident it is.

Using it

Calling a capability

$ cfcm invoke CapFoundry.geo.geocode Aarhus
{ "resolved": true, "status": "ok",
  "match": { "displayName": "Aarhus, Aarhus Kommune, 8000, Danmark",
             "lat": 56.1496278, "lon": 10.2134046, "countryCode": "DK" },
  "attribution": "Data © OpenStreetMap contributors, ODbL 1.0." }

A positional fills the next required field, --name value a named one, --a.b value a nested one.

Using it

Composition

$ cfcm invoke CapFoundry.geo.geocode Aarhus     → lat / lon
        ↓
$ cfcm invoke CapFoundry.geo.distance           → 289.4 km to Hamburg

Results go to stdout and diagnostics to stderr, so capabilities pipe together. Two capabilities, neither of which knew the other existed, composed by a caller who read two contracts.

The registry

Two ways to get an answer

return: "result"

Runs it and hands you the answer. You never see the implementation, and you do not have to maintain it.

return: "artifact"

Hands you the source, to put in your own project and ship. The registry becomes a library you copy from.

One registry serves both “answer my question” and “give me the code”, and each capability decides which it allows.

The registry

Contracts, not documentation

// capability.json
{ "name": "CapFoundry.geo.distance", "version": "1.0.0",
  "effect": "PURE", "exposure": "public", "permissions": {},
  "inputSchema":  { "…": "two coordinate pairs" },
  "outputSchema": { "…": "distance in metres and kilometres" },
  "sha256": "… sealed …", "tests": "…",
  "license": "Apache-2.0", "provenance": "…" }

A capability is a package you can verify, not a snippet you have to trust.

Guarantees

Effects the runtime enforces

PURE  no network · no filesystem · no clock · no randomness
      deno run --no-remote --no-npm  (no permission flags at all)
  • The artifact runs in its own subprocess, so the guarantee is the runtime’s, not the author’s.
  • Nothing can be loaded from outside the artifact — no remote import, no package registry.
  • A capability cannot quietly reach the network because it is never given the chance.
Guarantees

Network access is granted, never taken

// CapFoundry.geo.geocode declares what it needs
"effect": "NETWORK",
"permissions": { "network": ["nominatim.openstreetmap.org"] }

That is a request. CFCM intersects it with your own policy in cfcm.json, off by default — so it reaches exactly one host, only if you allow it, and no other.

Guarantees

It refuses rather than guesses

$ cfcm invoke CapFoundry.geo.geocode Viborg
{ "status": "ambiguous",
  "candidates": [ "Viborg, Denmark", "Viborg, South Dakota, US", "Viborg, Russia" ] }

$ cfcm invoke CapFoundry.geo.geocode Viborg --countryCode DK
{ "status": "ok", "match": "Viborg, Denmark" }

A registry that is embarrassed to say “I’m not sure” is worse than one that says nothing.

Yours

Your capabilities, your machine

CapFoundry.*

Public. The ten capabilities everyone gets, sealed and versioned.

Netsi.*

Private, registered in your own cfcm.json — so no central service knows your organisation exists.

Local.*

Machine-only, for trying something out before you publish it anywhere.

One search covers all three. A private capability can execute while refusing to hand back its source.

Yours

The registry grows from use

Candidates, not commits

When an agent writes something deterministic and generally useful that the registry lacked, it can offer it. Nothing is published automatically — a person reviews and promotes it.

Explore

A local page shows what is used most, and what is repeatedly asked for and missing. That second list is what to build next.

CapFoundry.text.editDistance joined the registry exactly this way: someone asked, there was no match, the agent wrote it and offered it.
